# BTech.NFe.Api — scripts de setup passam a criar o .env sozinhos

## Resumo
O Jonas relatou que os `.env` da API "não estão mais sendo commitados" depois de o script falhar
no Windows. Investigação: nunca foram. O que faltava era o script criar o arquivo — corrigido nos
quatro pontos de entrada.

## O que foi feito

### Diagnóstico
- `git log --all -- '*.env'` no [[BTech.NFe.Api]]: única entrada é `A .env.example` no commit
  `f1b5f78`. O `.env` nunca esteve no histórico.
- `.gitignore:6` cobre `.env` desde sempre; `git check-ignore -v .env` confirma.
- O `.env` local do Mac era **idêntico** ao `.env.example` (`diff` vazio) — nenhum segredo real,
  `FOCUS_NFE_TOKEN` e `SMTP_*` vazios.
- Causa do erro no Windows: clone novo não tem `.env`, e `run-local-api.ps1` abortava com
  `Write-Error "Env file not found"`.
- `docker compose up` não era afetado — todo `${VAR}` no compose tem default.
- O front ([[BTech.Web]]) já resolvia isso em `scripts/dev-local.ps1`. A API não. Era só assimetria.

### Mudanças (6 arquivos)
- `scripts/run-local-api.ps1` / `.sh` — criam o `.env` do `.env.example` em vez de abortar.
- `scripts/setup-local.ps1` / `.sh` — idem, antes do `docker compose up`, para haver onde preencher
  `FOCUS_NFE_TOKEN`/`SMTP_*`.
- `.gitattributes` — `.env.example text eol=lf`, senão o clone Windows gera `.env` CRLF e o loader
  do `.sh` leva `\r` para dentro da connection string (reproduzido: `Database=BTechPLUSTESTE^M;`).
- `INSTALLATION.md` — nota de que o `.env` não é versionado e que os scripts o criam.

### Validação
- `bash -n` e `[Parser]::ParseFile` nos quatro scripts.
- Clone simulado em sandbox, sem `.env`: `.sh` e `.ps1` criaram o arquivo, carregaram as variáveis
  e só pararam no `dotnet run` (o `src/` não existia no sandbox) — comportamento esperado.

## Commit
`edc9747` na branch **`fix/env-local-criado-pelos-scripts`**, criada a partir de `origin/main`.

A branch em que a sessão começou (`feature/dashboard-notificacoes-auditoria-e-focus-real`) já tinha
o PR **#36 mergeado por squash** — `git diff origin/main HEAD` vinha vazio, confirmando que o
conteúdo já estava na main. Commitar nela repetiria
[[branch-de-pr-ja-mergeado-acumula-trabalho-novo-sem-perceber]]; o `git checkout -b <nova>
origin/main` carregou as 6 modificações do working tree sem conflito, porque nenhuma delas dependia
do commit antigo.

Push feito e PR **#37** aberto: https://github.com/B-Tech-Sistemas/BTech.NFe.Api/pull/37 (base `main`, mergeable/clean).
